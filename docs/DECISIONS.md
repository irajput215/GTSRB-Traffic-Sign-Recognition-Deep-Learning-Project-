# Architecture Decision Records

Decisions that shaped this project, each with the alternatives that were actually
considered and the trade-off that was accepted.

These are written to be defensible in a technical interview: every "why" is
specific to *this* project, and every number is one that was measured. Where a
decision was reversed after a measurement, the reversal is included — the first
answer being wrong is more informative than a tidy list of correct ones.

## 1. PyTorch over TensorFlow/Keras

**Context.** The original project was already PyTorch (Colab, Python 3.11), and the
three architectures were written as `nn.Module` subclasses.

**Options considered.**

- *Rewrite in TensorFlow/Keras* — no benefit, and it would discard working code.
- *Keep PyTorch* — reuse the architectures and the training semantics.

**Decision.** PyTorch.

**Why.** The project's contribution is a controlled comparison of three
architectures, and that comparison already exists in PyTorch. Rewriting would
consume the entire refactor budget on a lateral move. Beyond that, the specific
things this project needs are all first-class in PyTorch: `torchvision` ships the
GTSRB dataset *and* the ImageNet-pretrained backbones, mixed precision is a
two-line change, and the `state_dict` contract is simple enough to make
self-describing. The transfer-learning branch needs pretrained ResNet-50 weights
plus the same `nn.Module` interface for freezing — both trivial here.

**Trade-offs.** TensorFlow has a more mature serving story (`TF Serving`,
`saved_model`). This project serves over HTTP with FastAPI instead, so it does not
need it. PyTorch's own serving options were not used either, for the same reason:
the checkpoint format needed to carry label names and normalisation statistics,
which a generic serving runtime would not preserve.

## 2. Keep the compact CNN as the default

**Context.** The recorded run compared three models. Accuracy on the test split:
compact CNN **98.84%**, ResNet-50 **96.97%**, MLP **65.84%**.

**Options considered.**

- *Default to ImageNet transfer learning* — the conventional 2026 answer, and the
  one the original report named as future work.
- *Default to the compact CNN* — the measured winner, at 64×64.

**Decision.** Compact CNN.

**Why.** Three reasons, in order of weight:

1. **It measured better on this dataset.** 98.84% against 96.97%. The original
   report's own explanation is plausible and specific: ResNet-50 was fine-tuned
   with only `layer4` unfrozen, and the ImageNet→cropped-sign domain gap is real.
2. **It is an order of magnitude cheaper to serve.** 9,557,483 parameters, 36.5 MB
   in memory, 64×64 input — roughly 1/12 the input pixels of ResNet-50 at 224×224.
   On the MPS machine used for verification, 64×64 inference was under 10 ms
   warmed.
3. **It keeps the from-scratch result honest.** The interesting claim in this
   project is that a task-specific compact network beat a much larger pretrained
   one. That claim only survives if the compact network is the one being served.

**Trade-offs.** The CNN has 9.6M parameters against the MLP's 27.9M — it wins on
*inductive bias*, not on size. It is also more brittle to input-domain shift than
a pretrained backbone: it has seen only GTSRB, so a different country's sign set
would likely need retraining rather than fine-tuning. ResNet-50 remains selectable
(`--set model.name=resnet50`), and `configs/model.yaml` documents the comparison,
so this is a default rather than a removal.

## 3. Keep the MLP baseline

**Context.** The MLP scores 65.84% and has no path to being served.

**Options considered.**

- *Delete it* — it is dead weight.
- *Keep it* — it is the control in the comparison.

**Decision.** Keep it.

**Why.** Without the baseline, "the CNN works" is an assertion rather than a
measurement. The comparison is also genuinely interesting in a way that is easy to
state: **the MLP has 27,940,907 parameters against the CNN's 9,557,483 — three
times as many — and scores 33 accuracy points lower.** That is the cleanest
available demonstration that parameter count is not the bottleneck for this
problem; the convolutional prior is. Both numbers are measured by
`summarise_model`, not estimated.

**Trade-offs.** ~120 lines of code that will never be deployed. Bounded, and it
pays for itself as the anchor of the headline comparison.

## 4. Weighted sampling instead of materialised oversampling

**Context.** GTSRB is long-tailed: 150 images for the rarest class against 1500 for
the most common, a 10× imbalance. The original materialised an oversampled index
list to a floor of 800 per class, growing the training set from 21,312 to 36,944.

**Options considered.**

- *Materialised oversampling* — what the original did.
- *`WeightedRandomSampler` with inverse-frequency weights* — standard PyTorch.
- *Class-weighted loss* — reweights the gradient rather than the data.
- *Do nothing* — accept the imbalance.

**Decision.** Weighted sampling, `weight ∝ count ** -power` with `power = 1.0`.

**Why.** Identical class balance to the original, with four concrete improvements:

- **Memory.** No 36,944-element index list built at dataset construction.
- **Effective epoch size.** A materialised list means the majority classes are seen
  the same number of times per epoch as a synthetic minority copy. Sampling keeps
  the majority classes at their natural rate while raising the minority rate.
- **Fresh draws.** Each epoch samples different minority images rather than one
  fixed repeated list, so the model sees more distinct minority examples overall.
- **RNG control.** A local `torch.Generator` rather than the global NumPy state,
  which the original used implicitly.

The achieved balance is **verified, not assumed**: `ClassWeights.effective_counts`
computes the expected per-class draw counts and they are written to the run log.

**Trade-offs.** An epoch is shorter than the original's (21,312 draws rather than
36,944), so a nominal 30 epochs is less compute than the original 30. This is
documented rather than hidden; the number of *distinct* images per epoch is
unchanged and the balance is equivalent, but a like-for-like epoch-count comparison
with the recorded run is not exact. Class-weighted loss was rejected because it
changes the gradient scale per class, which interacts with the learning rate; the
original report's own imbalance handling was data-side, and keeping that axis
consistent preserves the comparison.

## 5. Select on macro F1, not accuracy

**Context.** The original saved the checkpoint with the best validation accuracy.
The audit digitised the stored confusion matrix and found class 27 (Pedestrians) at
**54.2% recall**, with 29.5% predicted as 23 (Slippery road) and 16.3% as 30
(Beware of ice/snow) — all red warning triangles. Accuracy was 98.84%.

**Options considered.**

- *Keep accuracy* — parity with the recorded run.
- *Macro F1* — weights all 43 classes equally.
- *Balanced accuracy* — equivalent to macro recall.
- *Per-class loss weighting* — changes the objective, not just the selection.

**Decision.** `val_macro_f1` for checkpoint selection **and** early stopping.
Accuracy is still reported.

**Why.** Accuracy is dominated by the common classes. A model can sit at 98.8%
accuracy with one class at 54% recall, which is exactly what happened. Macro F1
makes a failing class cost ~1/43 of the score rather than ~1/43 of the errors, so
it selects the model that is actually better across the label space. For a
driver-warning system, silently failing on one sign type is the failure mode that
matters.

**Trade-offs.** Macro F1 is noisier than accuracy on rare classes, so the
early-stopping curve is less smooth. It also means the selected checkpoint may have
slightly *lower* accuracy than an accuracy-selected one — a deliberate trade of a
headline number for long-tail behaviour. Accuracy is still reported alongside, so
nothing is hidden.

## 6. Pydantic v2 + YAML configuration

**Context.** The original repeated normalisation constants verbatim in the training
transforms *and* again in each of the three evaluation calls, with image sizes,
batch size, epoch counts and learning rates as bare literals at their point of use.

**Options considered.**

- *`argparse` only* — no validation, no nesting, awkward for many parameters.
- *Hydra* — powerful, and the standard for research-scale config composition.
- *Plain dataclasses + YAML* — no validation beyond types.
- *Pydantic v2 + YAML* — validation, nested models, JSON serialisation.

**Decision.** Pydantic v2 models loaded from YAML with dotted `key=value`
overrides, plus `pydantic-settings` for environment variables.

**Why.** The requirement that decided it is **serialisation**. The resolved config
goes into the checkpoint and into MLflow as an artifact, so it must round-trip to
JSON losslessly — `model_dump(mode="json")` / `model_validate` does that with no
custom encoder. Frozen models with `extra="forbid"` turn a typo into a startup
failure instead of a silent misconfiguration, and per-field validators catch
nonsense early (a zero normalisation standard deviation, a `persistent_workers`
flag with no workers, a checkpoint monitor inconsistent with its mode).

Hydra was rejected as too much machinery for four configuration files and a flat
precedence chain; its composition and sweeps features are not used here, and MLflow
already covers the experiment-comparison need.

**Trade-offs.** Pydantic is a runtime dependency that a plain dataclass would not
need. Nested override strings (`--set training.optimizer.lr=1e-4`) are less
ergonomic than Hydra's `+trainer.lr=…` syntax, though values are YAML-parsed so
types are inferred rather than guessed.

## 7. Persist and verify the data split

**Context.** The original computed `train_test_split(..., stratify=labels,
random_state=43)` inside a notebook cell and never recorded the result. "We used
the same split" was unverifiable, and comparing two runs required trusting that
nobody edited the cell.

**Options considered.**

- *Recompute from the seed* — what the original did. Reproducible in principle.
- *Persist the index lists* — a manifest.
- *Move files into `train/` and `val/` directories* — the classic approach.

**Decision.** Persist indices **and** verify them on load.

**Why.** Persisting alone introduces a new failure mode: a manifest from a previous
dataset revision silently applied to a new one. `verify_manifest` therefore rejects
a manifest whose sample count, seed, or validation fraction has changed, whose
indices overlap or fail to cover the dataset exactly once, **or whose per-index
labels no longer match the dataset**. That last check is the important one — same
length, different labels, silent mis-split — and it is covered by a test.

The manifest stores the labels explicitly rather than only the indices, precisely so
that check is possible.

**Trade-offs.** A stale manifest is now a hard error requiring `--force-split`
rather than a silent recomputation. That is the intended direction: the failure it
prevents is a corrupted evaluation, and the fix is one command. Copying files into
`train/`/`val/` directories was rejected because it duplicates ~200 MB of data and
makes the split a filesystem fact that nothing verifies.

**Verified.** The refactored pipeline reproduces the original split exactly: 26,640
training images, per-class min 150 / max 1500, and 21,312 train / 5,328 validation
at seed 43.

## 8. MLflow, and only MLflow

**Context.** The original's only record of a run was whichever cell outputs happened
to be saved in the notebook.

**Options considered.**

- *Weights & Biases* — polished, excellent UI, hosted-first.
- *TensorBoard* — already a PyTorch fixture; great scalars, weak artifact model.
- *MLflow* — tracking, artifacts, model registry, self-hostable.
- *Plain JSON logs* — no dependency at all.
- *MLflow **and** one of the others* — what "modern ML stack" often means in
  practice.

**Decision.** MLflow only, as an optional extra.

**Why.** The decisive feature is the **model registry**, which answers "which
version is deployed?" — a question TensorBoard and JSON logs cannot. MLflow also
self-hosts with no account and no network, which matters because this project
should run end-to-end on a laptop. Every run records not only parameters but the
**resolved config as an artifact**, because neither the YAML layers nor the `--set`
overrides are recoverable from a run afterwards, and "which flags did we use?" is
exactly what a later reproduction attempt needs.

Adding a second tracker would be the "impressive stack" anti-pattern: two systems
recording the same metrics, neither authoritative.

**Trade-offs.** MLflow is a large dependency and is therefore an opt-in extra
(`uv sync --extra tracking`), with a `Tracker` protocol and `NullTracker` so the
training loop contains no tracking conditionals and works with nothing installed.
Its default `pt2` model serialisation had to be overridden (§10).

## 9. SQLite tracking backend, not the file store

**Context.** The obvious local MLflow backend is `file:./mlruns`.

**Options considered.**

- *`file:./mlruns`* — the documented, familiar local default.
- *`sqlite:///mlflow.db`* — a single local file, still no server.

**Decision.** SQLite. **This reverses the first implementation.**

**Why.** The file store no longer works with current MLflow. Every tracking call
raised:

```
MlflowException: The filesystem tracking backend (e.g., './mlruns') is in
maintenance mode and will not receive further updates. Please migrate to a
database backend (e.g., 'sqlite:///mlflow.db') to access the latest MLflow
features. ... If the filesystem backend is required for your workflow, set
`MLFLOW_ALLOW_FILE_STORE=true` to opt out of this exception.
```

A local SQLite file keeps every property that mattered about the file store — one
file, no server, no account, no network — on a backend that is supported. Opting
out via `MLFLOW_ALLOW_FILE_STORE=true` was rejected because suppressing a
maintenance-mode warning to keep a deprecated backend is the wrong default for a
project meant to look current.

**Trade-offs.** A `.db` file instead of a directory tree; slightly less convenient
to inspect by hand, though `sqlite3` is ubiquitous. Neither option supports
concurrent writers well, which is fine: this is a single-user local store.

## 10. Pickle model artifacts, not pt2

**Context.** MLflow 3.x defaults `mlflow.pytorch.log_model` to a `pt2`
traced-graph format. The first implementation used the default.

**Options considered.**

- *`pt2` traced graph* — the default; faster inference; exportable.
- *`pickle`* — the long-standing PyTorch format; stores the live `nn.Module`.

**Decision.** `pickle`. **This reverses the first implementation, after measuring.**

**Why.** Two concrete failures with the traced graph:

1. **It accepts only the batch size it was traced with.** A model logged from a
   batch of 1 rejected a batch of 2 with `Guard failed: x.size()[0] == 1`. The
   signature is inferred from a fixed input example, and the exported graph bakes
   that example's shapes in. A registry artifact that only serves batch size 1 is
   not a useful artifact.
2. **`.eval()` raises `NotImplementedError`** on a traced module, because there is
   no training state left to switch.

`pickle` stores the live module, so the registered model accepts any batch size and
behaves like the model that was trained.

**Trade-offs.** Losing the traced graph's inference speed-up. This does not apply
here: the inference service loads the project's **own checkpoint format** rather
than an MLflow artifact, because a checkpoint also carries the class-label
ordering, input geometry and normalisation statistics that the API needs to
preprocess a request correctly. The MLflow artifact exists for the registry and
lifecycle, not for serving.

**Verified.** Round-trip tests load the logged model from both `runs:/…` and
`models:/<name>/<version>` URIs and predict on batch sizes 2 and 4.

## 11. FastAPI for inference

**Context.** The trained model had no inference path outside the notebook: producing
one prediction meant re-running cells up to the checkpoint load.

**Options considered.**

- *A Python script* — simplest; unusable by anything but a Python caller.
- *`torchserve` / `TF Serving`* — purpose-built model servers.
- *FastAPI* — a thin Python HTTP layer over the predictor.
- *Flask* — simpler, synchronous, no schema generation.

**Decision.** FastAPI.

**Why.** The project already has Pydantic models for the response contract, so
FastAPI turns them into validated responses **and** generated OpenAPI documentation
at no extra cost — the request and response schemas are the documentation, and they
cannot drift. It is async-capable for the upload path, and its dependency-injection
style puts the model on `app.state` rather than in a module global, which is what
makes the app testable without a checkpoint.

`torchserve` was rejected because the model is 36.5 MB, CPU-servable in
milliseconds, and needs custom input validation that a generic server does not
provide; the operational machinery would dwarf the two endpoints. Flask was
rejected because it would mean hand-writing and maintaining an OpenAPI schema,
which is exactly the kind of documentation that rots.

**Trade-offs.** single-process uvicorn, so one slow request occupies the event loop
for its duration. Measured inference at 64×64 is a fraction of a millisecond on
GPU and under 10 ms on CPU, so this has not mattered. A GPU deployment would want
`--workers` and would accept per-worker model copies. Authentication and rate
limiting are explicitly **not** implemented — they belong at the ingress, and a
token in an environment variable would be worse than being explicit about it.

## 12. Pillow, not OpenCV

**Context.** The API must decode arbitrary uploaded images and transform them for
the model.

**Options considered.**

- *OpenCV (`opencv-python-headless`)* — fast, ubiquitous in CV projects.
- *Pillow* — already present via torchvision.
- *`torchvision.io`* — tensor-native decoding.

**Decision.** Pillow.

**Why.** Pillow is **already a transitive dependency** of torchvision, so this adds
zero bytes and zero version surface. It decodes every format an API is likely to
receive (PNG, JPEG, PPM, BMP, WebP, TIFF), handles EXIF orientation, and raises on
truncated files — which the validator relies on. OpenCV would add a large compiled
dependency plus its own `libGL`/`libglib` requirements in the container, to solve
problems this project does not have: no feature detection, no video, no camera
capture. `torchvision.io` was rejected because `Transforms` v2 and the dataset
pipeline are PIL-based, so mixing would mean two decode paths.

**Trade-offs.** OpenCV is measurably faster at decode-and-resize for large images.
Not relevant at these sizes. Pillow's `Image.MAX_IMAGE_PIXELS` guard is set
explicitly rather than left at the default, since uploads are untrusted.

## 13. Docker with CPU-only PyTorch

**Context.** The inference service needs to be containerised. The first working
image was **9.63 GB**.

**Options considered.**

- *Default `pip install torch`* — pulls the CUDA build on Linux.
- *`UV_INDEX_URL` pointing at the PyTorch CPU index* — the obvious fix; **it did
  not work.**
- *Declare the CPU index in `pyproject.toml` as a uv source* — makes the lock
  itself CPU-only.
- *Multi-stage build* — trim the toolchain from the runtime image.

**Decision.** CPU torch declared as a uv source, plus a two-stage build. Final
size **1.8 GB**, an 81% reduction.

**Why, and why the obvious fix failed.** Setting `UV_INDEX_URL` in the Dockerfile
had **no effect** — the build produced the same 9.63 GB image. The reason: the
**lock file**, not the index URL, decides what `uv sync --frozen` installs. A
build-time index override is silently ignored against a lock that points at PyPI.
Declaring the index and source in `pyproject.toml` makes the lock itself CPU-only,
with platform markers so macOS still resolves its own wheel:

```toml
[[tool.uv.index]]
name = "pytorch-cpu"
url = "https://download.pytorch.org/whl/cpu"
explicit = true

[tool.uv.sources]
torch = { index = "pytorch-cpu" }
torchvision = { index = "pytorch-cpu" }
```

That first measurement is worth stating plainly: 3.3 GB of `nvidia` runtime
libraries and 817 MB of `triton`, for a service that runs on CPU. Removing an
unused `pandas` dependency took it from 1.9 GB to 1.8 GB.

**Trade-offs.** The image will not use a GPU. A GPU deployment changes the index
and drops `GTSRB_DEVICE=cpu`. Two stages add a little build complexity in exchange
for the toolchain not shipping, and for a dependency layer that survives source
edits. Roughly 210 MB of the remaining size is `scikit-learn` + `matplotlib` +
`scipy`, which are evaluation and plotting dependencies the API does not need;
splitting them into a `[train]` extra is documented as the next optimisation rather
than done, because it changes what a bare `pip install` provides for a 12%
reduction.

## 14. No Kubernetes, no cloud ML platform

**Context.** A production ML project "should" arguably have Kubernetes manifests,
Terraform, or a managed platform (SageMaker, Vertex AI, Databricks).

**Options considered.**

- *Kubernetes manifests + Helm* — the conventional "production" signal.
- *A managed cloud ML platform* — SageMaker endpoints, Vertex AI.
- *Docker Compose only* — a documented `docker run` and a compose file.

**Decision.** Docker only. No orchestrator, no cloud resources.

**Why.** The service is **one stateless container serving one HTTP API**. It has no
scheduling constraints, no service mesh requirement, no autoscaling signal that a
single load balancer cannot act on, and no persistent state. Kubernetes would add
hundreds of lines of YAML, a cluster dependency, and a whole class of failure modes
— and none of it would be exercised, so none of it would be trustworthy.

A managed platform was rejected for the same reason plus a worse one: it would put
the deployable artifact behind an account and a bill, making the project harder for
anyone to run. The honest position is that the architecture *is* deployable —
stateless, health-checked, configurable by environment, with readiness separate
from liveness — and the orchestration layer is a deployment choice rather than an
architectural one. `docs/DEPLOYMENT.md` documents how it would scale horizontally
and what would change on GPU nodes.

**Trade-offs.** No autoscaling, no rolling deploys, no secrets management. All real
gaps, all named in the limitations section rather than glossed. The project
demonstrates the ML lifecycle and the service; it does not claim to demonstrate
cluster operations.

## 15. CLIs in the package, scripts outside it

**Context.** The conventional layout has `scripts/train.py`, `scripts/evaluate.py`,
`scripts/predict.py`.

**Options considered.**

- *`scripts/` wrappers* — conventional; matches most project templates.
- *Entry points in `src/gtsrb/cli/`* — importable, installable, testable.
- *Both* — a wrapper layer over the real implementation.

**Decision.** Entry points in `src/gtsrb/cli/`, exposed as console scripts
(`gtsrb-train`, `gtsrb-evaluate`, `gtsrb-predict`, `gtsrb-serve`). `scripts/` is
reserved for things that genuinely are not part of the package interface.

**Why.** A console script is importable, so its argument parsing and its `run()`
can be unit-tested; it is installable, so `gtsrb-train` works after `pip install`
from any directory; and its dependencies are expressed by the extras that contain
it. A loose script in `scripts/` is none of those, and it only works when run from
the repository root — which is how the notebook's `test_loop()` came to depend on
hard-coded `/content/dataset/` paths.

Having both would be the worst option: two entry points to keep in sync, and the
one people actually run would be the untested one.

**Trade-offs.** Slightly less conventional, so a reader looking for `scripts/train.py`
has to be told where it went — which the README and `docs/ARCHITECTURE.md` §10 both
do. `scripts/` still holds four genuinely script-like tools: dataset preparation,
the config gate, the model-quality gate, and diagram generation. None of them is
part of the package's interface, so the split is a real distinction rather than a
relocation.

## 16. Diagrams generated by code

**Context.** The README needs architecture diagrams, and "professional diagram" is
usually read as "export a PNG from a drawing tool".

**Options considered.**

- *Hand-drawn exports (draw.io, Excalidraw, Figma)* — best-looking, fastest to
  start.
- *Mermaid only* — diffable, maintainable, but not rendered everywhere.
- *Mermaid plus code-generated PNGs* — both, from the same source of truth.
- *ASCII art* — renders everywhere, looks like a text file.

**Decision.** Mermaid in `docs/ARCHITECTURE.md` as the maintainable source, plus
PNGs generated by `scripts/export_docs_assets.py` for the README.

**Why.** A hand-drawn PNG is a binary blob that nobody can review: a change to the
architecture produces a diff that says "binary file changed", and the diagram
silently becomes wrong. Here the diagrams are code, so a change to a stage is a
reviewable diff and regeneration is one command. Mermaid alone was rejected because
GitHub renders it but many other viewers do not, and a README whose central diagram
fails to render is worse than one with a static image.

**Trade-offs.** Code-generated diagrams look more schematic than a designed one —
they are box-and-arrow flows, not illustrations. Accepted: consistency and
reviewability matter more here than visual flourish. Maintaining both forms is
duplication, mitigated by keeping the Mermaid as the flow of record and the PNGs as
a rendering of the same stages.

## 17. A self-describing checkpoint

**Context.** The original saved `model.state_dict()` to `gtsrb_cnn.pth`. Producing
one prediction from it required re-running the notebook up to the model definition:
the architecture, the input size, the normalisation statistics and the class
ordering all lived in cells.

**Options considered.**

- *`state_dict` plus a sidecar JSON* — two files that can drift apart.
- *`state_dict` plus a config path recorded inside* — the path can move or change.
- *One file with weights, the full resolved config and the label space.*

**Decision.** One file, versioned, carrying weights, the resolved config, the class
names, the input geometry, the normalisation statistics, the metrics at that epoch,
the git commit and the library versions.

**Why.** Inference then needs nothing but the checkpoint path, and three failure
modes become impossible:

1. **Architecture drift** — the model is rebuilt from the stored config, so serving
   cannot use a different architecture than training did.
2. **Preprocessing drift** — normalisation statistics come from the checkpoint, so a
   later config edit cannot silently degrade predictions. This is the most
   dangerous failure of the three because it produces no error at all.
3. **Label-space drift** — the class names are stored and validated against the
   canonical ordering at load time, so a checkpoint trained under a permuted mapping
   is rejected instead of serving confidently wrong names.

`format_version` allows the layout to change later without a silent misread, and
writes are atomic so an interrupted save cannot destroy the previous best.

**Trade-offs.** Larger checkpoints and a loader that must handle more error cases —
all of which are tested. `best.pt` deliberately omits optimiser state: it is the
served artifact, and including Adam's two moment buffers per parameter tripled it
(114 MB for a 36.5 MB model). `last.pt` keeps the full state for resuming, which is
a distinction worth documenting because "resume from `best.pt`" now fails
deliberately.

## 18. Reported metrics stay the original run's

**Context.** The README needs results. The refactored pipeline can be run to
produce new ones, but the machine available is an 8 GB M1 with no CUDA GPU.

**Options considered.**

- *Report the original notebook's numbers as if the refactor produced them* —
  **fabrication. Rejected outright.**
- *Report no metrics at all* — safest, but a portfolio project with no measured
  results is much weaker.
- *Report the original numbers, clearly attributed, plus every measured fact the
  refactor did produce.*

**Decision.** The third.

**Why.** The original numbers are real measurements from a real run; the problem
would be misattributing them. The README therefore states, next to the table, that
those figures come from the recorded Colab A100 run of the original notebook, and
that the refactored pipeline reproduces the setup with `make train`. Separately, it
reports what *was* measured during the refactor: the split reproducing exactly
(26,640 → 21,312/5,328), parameter counts, checkpoint sizes, per-epoch wall-clock
time, container size, and inference latency.

The alternative — quietly presenting inherited numbers as new — is the single most
common way an ML portfolio project becomes indefensible under questioning. If an
interviewer asks "did you run this?", the answer needs to be true.

**Trade-offs.** The README's headline table is not produced by this repository's own
command. That is stated rather than implied, and the reproduction command is given.
A genuine 30-epoch run was in fact started in the background during the refactor;
whatever it produced is reported as measured-and-attributed separately, never
merged into the original table.

## 19. No test requires the dataset

**Context.** Most of this project's behaviour depends on GTSRB, a ~300 MB download.

**Options considered.**

- *Download the dataset in CI* — realistic, but slow and brittle.
- *Commit a small subset* — adds data to git, and a subset is not the dataset.
- *Synthetic fixtures and skip-when-absent integration tests.*

**Decision.** The third.

**Why.** A test suite that needs a 300 MB download is a test suite nobody runs, and
one that fails on a fresh clone teaches people to ignore it. Synthetic fixtures —
sign-like images with per-class colour structure, and tiny models — cover the
behaviour that matters: shapes, invariants, error paths, contracts. Tests that
genuinely need the real data are marked `integration` and skip cleanly when it is
absent, so the **same command** works on a laptop, in CI and on a fresh clone.

This also paid for itself: writing the integration tests surfaced a performance bug
where reading labels through `__getitem__` decoded all 26,640 images, because
torchvision's GTSRB decodes the PNM before returning the label. Since manifest
verification reads every label on every run, that was ~30 s per call. Fixing it took
the suite **from 216 s to 8 s**.

**Trade-offs.** Synthetic images are not real traffic signs, so a test can pass
while the real pipeline is subtly wrong — the reason the skip-when-absent
integration tests exist and are run when the data is present. The dataset-dependent
behaviour that no unit test can reach (real split reproduction, real class
distribution) is verified by `scripts/prepare_data.py` and by the scheduled
`model-validation` workflow.

## 20. Separate model-validation workflow

**Context.** CI should verify that training still works.

**Options considered.**

- *Train on every PR* — maximum confidence, maximum cost.
- *A short smoke train on every PR* — one epoch, ~10–20 min on a hosted CPU runner.
- *A separate workflow, on demand and weekly.*

**Decision.** A separate workflow on `workflow_dispatch` and a weekly schedule,
never on a PR.

**Why.** Training is minutes to hours, and gating a PR on it would make CI slow
enough that people route around it — the same reasoning as §19. A one-epoch smoke
run on every PR was the closest call: it would catch a broken data pipeline
immediately. It was rejected because an epoch on a hosted two-core runner is long
enough to dominate the whole pipeline, and because a one-epoch model tells you
almost nothing about quality — the recorded run was at 17.7% validation accuracy
after one epoch.

The workflow instead does the whole loop and gates on a **quality floor**:
download, validate the dataset, train for a configurable number of epochs, assert
`val_accuracy` above a threshold, evaluate on the test split, then **serve a real
prediction** from the produced checkpoint. The floor is a CLI argument because the
right threshold depends on how long the run was allowed to train, and the API check
asserts the *response contract* rather than the answer — after a few epochs the
correct class is not guaranteed, so asserting it would make the workflow flaky
rather than meaningful.

`scripts/check_model_quality.py` fails on a below-floor value, too few epochs, a
missing checkpoint, **and a missing or malformed result file** — a gate that can be
satisfied by an absent file is worse than no gate. That case has a test.

**Trade-offs.** A regression in the training path may reach `main` before the
weekly run catches it. Mitigated by the fast jobs: `lint`, `typecheck`, `test` and
`docker` all run on every PR, and the unit and integration suites cover the
training loop's logic with tiny models. What only the scheduled workflow can catch
is real-data rot — a changed dataset URL, a `torchvision` API change — which is
exactly what a weekly cadence is for.
